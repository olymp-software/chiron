# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Chiron is a local desktop app for taking interactive IT courses: it adds a course (git repository or local folder), renders its content and runs the course's shell scripts on the learner's machine. Stack: Go + Wails v2 + Vue 3 (TypeScript). v1 ships for Windows amd64/arm64 only, but `internal/` must stay portable to Linux/macOS. Development happens in WSL; Windows binaries and tests run via WSL interop.

## Commands

Tasks are in `Taskfile.yaml` (go-task). `task` / `task check` runs everything CI runs.

Always run tests and linters through `task`, never by calling `go test`, `golangci-lint`, `npm`/`npx` directly — direct runs create unwanted directories in the repo root.

- `task frontend:check` — eslint, prettier check, `vue-tsc`, vitest
- `task go:test` — `go test ./internal/...` for the host OS
- `task go:test:windows` — same tests built as Windows exes (`WIN_ARCH=amd64|arm64`, default arm64)
- `task go:lint` — golangci-lint of the whole module with `GOOS=windows`; builds `frontend/dist` first because the root package `//go:embed`s it
- `task go:lint:internal` — lint only `internal/` for the host OS (no frontend build needed)
- `task go:fmt`, `task frontend:format`
- `task build` / `task run` — build `build/bin/chiron.exe` and start it via WSL interop; `task dev` — `wails dev` (needs cgo)

Single tests: extra args pass through after `--`.
- Go: `task go:test -- -run TestName` (always runs over `./internal/...`) (same for `go:test:windows`)
- Frontend (paths relative to `frontend/`): `task frontend:test -- src/markdown/markdown.test.ts -t "name"`

Only `./internal/...` is tested; the root `main` package needs `frontend/dist` and the Wails toolchain.

## Architecture

- `main.go` / `app.go` (root package): Wails wiring. `App` is the only bound object — a thin facade delegating to `internal/library`. Its methods never return Go `error` (Wails would stringify it); they return `*Result` structs with an `Error *apperr.Error`. Uncoded errors are logged and replaced with `apperr.Internal`.
- Wails generates `frontend/wailsjs/` (bindings for `App` and `models.ts`) — regenerated by `wails dev`/`wails build`, don't hand-edit.
- The Wails asset server falls back to `library.FilesHandler()` for paths not in the embedded assets: course images are served at `/course-files/<storage key>/<path>`, images only, confined to the course copy via `os.Root`.

`internal/` packages:
- `apperr` — every learner-facing error is a `Code` (plus params and per-field `Problems`); Go never produces user-facing text. Adding a code: add the constant **and** list it in `All`, run `go generate ./internal/apperr` (writes `frontend/src/errors/codes.ts`), and add `errors.<code>` messages to both `frontend/src/i18n/en.json` and `ru.json`. Tests on both sides fail if any of these drift.
- `library` — `library.json` (versioned format, atomic writes) plus app-owned course copies under `<data>/courses/<key>`; add/Sync of local-folder courses, course overview; `Open` repairs copies left by an interrupted add/Sync. Global mutex for `library.json`, per-storage-key locks for copies.
- `source` — normalizing course sources, deriving storage keys (`<label>-<hash>`), copying folders.
- `manifest` — parses and validates `course.yaml` against the JSON Schema in `schemas/course/v1.json` (embedded via `schemas/`, also published for authors), then semantic checks; problems carry YAML paths.
- `runtime` — runs control scripts with the embedded `mvdan.cc/sh` interpreter (no system shell) plus built-in utilities.
- `platform` — per-OS data/log dirs, atomic file writes, log setup.

OS-specific code uses `_windows.go` / `_other.go` / `_unix.go` / `_darwin.go` / `_linux.go` suffixes; such files are linted only on their own OS, so check both `task go:lint` (Windows) and `task go:lint:internal` (host).

Frontend (`frontend/src`): no router — `App.vue` switches between `library/LibraryView` and `overview/CourseOverview`. UI strings go through vue-i18n (`en`, `ru`). `markdown/` renders course Markdown (markdown-it + shiki, custom dialect, link and image rewriting to `/course-files/`).

## OpenSpec workflow

Requirements live in `openspec/specs/<capability>/spec.md`; work is done as changes in `openspec/changes/<name>/` (proposal, design, delta specs, tasks), archived to `openspec/changes/archive/` when done. Use the `opsx:*` / `openspec-*` skills. Write all OpenSpec artifacts in English.

`openspec/config.yaml` defines the domain glossary (Learner, Author, Course source, Course copy, Storage key, Local-folder course, Sync, Activity, Theory block, …) with words to avoid (e.g. "user"/"student" → Learner, "lesson" → Activity, "course id" → Course source / Storage key). Follow it in code, comments, UI strings and specs.
